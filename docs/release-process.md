# QRNix Firmware Release Process

## Principles

- The tag is the release authority. The version string compiled into the
  firmware must equal the tag; `scripts/release.sh` aborts the release if it
  does not.
- The artifact is always built from the tagged commit, never from a later
  tree.
- A published tag is never mutated. Bugs found after publishing are fixed on
  `main` and shipped as the next patch release.
- All publishing goes through `scripts/release.sh`. No hand-published
  releases: skipping the script removes the version check.

## Commit convention

Changelogs are generated from the commit log, so commit subjects use a type
prefix. git-cliff groups them into sections:

| Prefix      | Changelog section |
|-------------|-------------------|
| `feat:`     | Features          |
| `fix:`      | Bug Fixes         |
| `docs:`     | Documentation     |
| `refactor:` | Refactoring       |
| `build:`    | Build System      |
| `chore:`    | Miscellaneous     |

Unprefixed subjects are filtered out of the changelog by git-cliff's default
configuration (`filter_unconventional = true`). To include them in a generic
bucket instead, create a `cliff.toml` via `git-cliff --init` and set
`filter_unconventional = false`.

## Changelog

Generated by [git-cliff](https://git-cliff.org) from commits between tags.
Install the prebuilt binary (Linux x86_64, verify the version on the release
page):

```bash
curl -LO https://github.com/orhun/git-cliff/releases/latest/download/git-cliff-2.13.1-x86_64-unknown-linux-gnu.tar.gz
tar xzf git-cliff-2.13.1-x86_64-unknown-linux-gnu.tar.gz
mv git-cliff-2.13.1/git-cliff ~/.local/bin/
```

Note: the tarball's top-level directory is `git-cliff-<version>` (no arch
suffix). The built-in defaults work without a `cliff.toml`; run
`git-cliff --init` only to customize sections or add links.

Useful commands:

```bash
git-cliff --unreleased     # preview the next release's notes
git-cliff -o CHANGELOG.md  # regenerate the committed changelog
```

## Versioning

SemVer tags with a `v` prefix: `v0.3.6`.

The user-visible version is `SOFTWARE_VERSION` in `src/qrnix.cpp:85`. It is
edited by hand during release prep; `scripts/release.sh` asserts that the
compiled string matches the tag before anything is published.

## Release steps (example: v0.3.6)

### 1. Develop

Merge `feat:`/`fix:` commits to `main` using the prefix convention.

### 2. Prepare the release

```bash
git-cliff --unreleased          # review what the notes will say
```

1. Edit `src/qrnix.cpp:85`: `SOFTWARE_VERSION` `"0.3.5"` -> `"0.3.6"`.
2. `git-cliff -o CHANGELOG.md` to regenerate the full changelog.
3. Commit: `git add -A && git commit -m "Prepare release v0.3.6"`.
4. `git push origin main`.

### 3. Release

```bash
scripts/release.sh v0.3.6
```

The script, in order:

1. Checks prerequisites (tools, `main` branch, clean tracked tree; the tag
   must not exist, or must exist and point at HEAD).
2. Generates release notes from the commit log (`git-cliff --unreleased`, or
   the `v0.3.5..v0.3.6` range when the tag already exists; `git log` fallback)
   and shows them for review.
3. Creates annotated tag `v0.3.6` if it does not exist yet, otherwise reuses
   it.
4. Builds: `pio run -e teensy40`.
5. Asserts `firmware.elf` contains the version string `0.3.6`.
6. Packages `dist/qrnix-teensy40-v0.3.6.hex` and hashes it locally.
7. Pushes `main` and the tag.
8. Creates the GitHub release with the hex and the notes.
9. Reads the digest GitHub computed for the uploaded asset and asserts it
   equals the local hash. If the digest cannot be read after retries, it
   warns and exits 0 so the release is not left half-finished; verify
   manually on the release page.

Dry run (build, assert, package; no tag, no push, no publish):

```bash
scripts/release.sh v0.3.6 --dry-run
```

### 4. Verify the published artifacts

```bash
sha256sum dist/qrnix-teensy40-v0.3.6.hex
```

Compare the output with the `sha256:` digest shown next to the asset on the
release page (it has a copy button). GitHub computes that digest from the
uploaded bytes, so a match proves the download is byte-identical to the
released build. The release script performs the same comparison
automatically after each upload.

The device boot splash shows `0.3.6`, the release title says `v0.3.6`, and
the checksum matches: three independent confirmations of what is on the
hardware. The hash guarantees the downloaded hex is byte-identical to what
was built from the tagged commit; it does not by itself prove authenticity
(that would need a signed checksum file) or bit-reproducible builds.

## Error handling

- Version mismatch or build failure before the tag is pushed: fix, commit,
  delete the tag (`git tag -d v0.3.6`), re-run.
- Publish step fails after the tag was pushed: the tag exists and points at
  HEAD, so the script reuses it and re-runs cleanly. A tag pointing at a
  different commit is refused; fix that deliberately.
- Bug found after publishing: never touch the released tag. Fix on `main`
  and release `v0.3.7`; its changelog diff `v0.3.6..v0.3.7` contains exactly
  the fix commits.
